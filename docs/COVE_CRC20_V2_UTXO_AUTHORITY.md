# Cove CRC-20 v2 UTXO authority

Status: implementation specification. The v1 script-account marketplace is disabled. Beads `covedao-433` and its child tasks gate release. This specification applies only to Cove-issued deployments; LEAF and other Garden tokens are not indexed or traded by Cove.

## Evidence and safety limit

A confirmed Garden LEAF sale, `051a113e68b1dc49aeb15d475a94d44af24ce1534f44a221c6490833960178e9`, spends two 670-sat seller outputs from setup transaction `942d81b150fd173b195248cfe13d7e9c4724b30acb44b848588e9f307dbd02fa`. Both seller witnesses use `SIGHASH_SINGLE|ANYONECANPAY` (`0x83`). Its vout 0 pays the seller 87,168 sats, vout 1 carries `{"p":"crc-20","op":"transfer","tick":"LEAF","amt":"3313800000000"}`, and vout 2 is a 1,000-sat buyer output. This establishes that BTC payment and a CRC marker can share one Bitcoin transaction. It does not reveal Garden's off-chain token debit rule or prove token atomicity. Cove does not reuse its signature layout.

Four other confirmed LEAF sales—`532f22d0edcd848d28b81ddb6b089402860d01fda2ec1fdb9701ea13bb0a2dcd`, `7ca60051e0ca4ea20dfdfa7c6a893e224c32f6b85773db93e500fd75de757565`, `99ecfd349de7a85dac3b8ea7a467eb65e9d3e411f449b3b38a9586259f1c86f0`, and `0ad3d888d05974ec76a63b9fd5c16f3628438e73684bffef815c61fa2fafe9d6`—also use two seller setup inputs, marker vout 1, and buyer vout 2, with marker amounts 6.8e12, 5e12, 2e12, and 1e13 atoms respectively. They reinforce the observable transaction layout, without establishing Garden's balance rule.

Another confirmed LEAF sale, `ba02e28478f3e5f5bfcbdfd1b137ecfceb50d4db47347ef0c21c15d97e889f1b`, spends two 670-sat seller setup outputs at inputs 0 and 1, both signed with `0x83`. Vout 0 pays the seller 381,340 sats, vout 1 marks a 20e12-atom LEAF transfer, and vout 2 pays 1,000 sats to a `bc1p…garden` address. Seven 67,000-sat inputs from that Garden address also fund the transaction. This is another observable payment and marker layout; it does not establish Garden's off-chain debit rule or make the address an ordinary buyer in every sale.

The current Cove v1 ledger attributes token balances to scripts. A transfer may debit that balance by spending any BTC UTXO at the script. `packages/crc20-ledger/test/escrow-threat.test.ts` demonstrates a seller transfer using an unrelated UTXO, a same-script escrow recovery spend, an unrelated vault break, and a predeposit transfer reordered by reorg. In each case Bitcoin-valid BTC payment can survive while v1 CRC replay rejects the expected token credit.

V2 binds each token allocation to a specific Bitcoin outpoint. A valid transfer consumes that outpoint, so an earlier transfer, burn, or competing fill conflicts with a later fill at Bitcoin consensus. Bitcoin still does not enforce CRC marker semantics. The official app and Guardian must independently validate the same deterministic v2 rules before a buyer signs and before broadcasting. A malicious signer or invalid raw transaction outside those clients can still burn tokens or pay BTC without valid CRC credit; v2 is not an on-chain covenant.

## Deployment and marker version

Only a registered deploy with `{"p":"crc-20","op":"deploy","tick":"COVE","type":"bonding","max":"2100000000000000","cv":"cove-curve-v2"}` creates a v2 asset. Identity is `(network, deployTxid)`, never ticker alone. The v1 curve economics and exact vault reserve equations remain versioned and testable; the deploy's `cv` selects the v2 ownership rules. A mainnet deployment must use a fresh v2 txid. Existing v1 script-account balances cannot be mapped to unique token outpoints without inventing ownership, so no automatic v1-to-v2 migration is allowed.

Every v2 mint or transfer marker contains numeric `"v":2` in addition to the existing `p`, `op`, `tick`, `amt`, and `id` fields. The canonical writer order is `p,op,tick,amt,id,v,ch`, omitting `ch` only when no token change exists. `ch` is an optional numeric output index, not an amount. For example, a partial transfer is `{"p":"crc-20","op":"transfer","tick":"COVE","amt":"100000000000","id":"<deploy txid>","v":2,"ch":2}`. Readers accept only these exact fields, canonical positive decimal `amt`, integer `v=2`, integer `ch` within the actual outputs, one marker at vout 0, and the configured marker size and relay policy. A v1 marker cannot mutate a v2 asset and a v2 marker cannot mutate a v1 asset. The base CRC transfer fields remain readable by generic CRC viewers; `id`, `v`, and `ch` are Cove extensions.

## Token-bearing outpoints

The canonical table key is `(network, deployTxid, txid, vout)`. A row records exact `atoms`, `scriptPubKey`, creation block, and canonical spend or burn. One output carries at most one Cove asset in v2. Every live token-bearing input of the relevant asset is consumed in full. Ordinary BTC inputs at the same script with no token row carry **zero** authority. Inputs bearing another asset are rejected in a v2 operation. If a token-bearing output is spent without a valid matching v2 transition, its allocation is burned; it does not remain available at its prior script. The supply equation is `lifetimeMinted = liveVaultInventory + liveUserAllocations + burnedAtoms`. Burn and all allocation changes roll back with the block.

The marker `amt` specifies atoms credited to recipient vout 1. All token inputs for a peer transfer must have the same owner script and appear as a contiguous prefix starting at input 0. Their sum must be at least `amt`. If the sum equals `amt`, `ch` must be absent. If the sum exceeds `amt`, `ch` must name exactly one spendable output with the same owner script and dust-sufficient BTC; that output receives the exact remainder. No second token change output, implicit script balance, or silent remainder is allowed. A self-transfer or consolidation follows the same equation. Wallet funding inputs follow the token prefix and must not carry Cove tokens.

The indexer derives input allocations from its canonical UTXO table and verified parent outpoints; it never trusts a client-supplied token amount or token-input count. If an input row exists for this asset outside the required prefix, the transaction is invalid and that spent allocation is burned. The input and output topology fixes the recipient and change allocation without adding amounts to the marker. A recipient can hold many separate token UTXOs; wallet balances sum their live amounts, while spending selects exact outpoints.

## Curve operations

Mint: input 0 spends the current vault; the exact `amt` new atoms are allocated to recipient output 1. The successor vault output remains at the existing v1 position and keeps the exact reserve delta. No token-bearing wallet funding input may be hidden among BTC inputs. Buying from vault inventory uses `op:"transfer"`: input 0 is the current vault token-bearing outpoint; output 1 receives `amt`, and the successor vault output receives old inventory minus `amt`. A buy crossing the inventory-to-mint boundary remains split into two transactions.

Sell to vault: input 0 spends the current vault and seller token-bearing inputs follow contiguously. The seller inputs must share a seller script; their sum is at least `amt`. The successor vault output receives prior vault inventory plus `amt`, and the reserve and BTC payout match the exact curve quote. Any seller token remainder goes to the single `ch` output with the seller script. Additional BTC funding inputs have no token allocation. A vault outpoint spent outside a valid transition makes **backing trading** unavailable; existing circulating token UTXOs remain transferable and marketable, with the backing failure shown to buyers. This separation prevents an unrelated vault failure from making a Bitcoin-valid peer fill lose token validity after signing.

## Marketplace exact fill

The first market release lists one exact token-bearing outpoint. Partial listings require a prior self-transfer that splits a carrier into a listing-sized output and a change output. The fill spends the listed token outpoint at input 0 and buyer BTC funding inputs after it. Vout 0 is the v2 transfer marker for the exact listed allocation; vout 1 is the buyer token carrier; vout 2 returns the seller's carrier sats plus net sale price; vout 3 pays the configured protocol fee; an optional final output returns buyer BTC change. `ch` is absent because the listed token outpoint is spent in full. Seller and buyer each sign the complete transaction with `SIGHASH_ALL` (or Taproot default with equivalent all-input/all-output commitment). The server checks the indexed token outpoint and fee terms before building, at seller signing, and before broadcast; Core checks current UTXO availability. Database reservation serializes local requests, while Bitcoin input conflict resolves competing chain transactions.

If the seller spends the listed token outpoint in another transfer or an unmarked burn, the fill cannot confirm. If a reorg inserts that spend before the fill, both spend the same outpoint and cannot coexist in the replacement chain. A different ordinary UTXO at the seller script has no authority over the listed token allocation. A malformed market transaction can still pay BTC if a buyer signs it, so the official wallet must verify the exact marker, token-input outpoint, recipient, payout, fee, miner fee, and change before exposing the signing prompt. No reusable `SIGHASH_SINGLE|ANYONECANPAY` seller signature is used.

## Indexer, reorg, and migration gates

Persist token UTXO allocation/spend/burn changes and the block undo in one database transaction with the canonical cursor. Projected script balances are sums of live token outpoints; they are not independent authority. Same-height and deep reorgs restore the exact UTXO set, backing status, burned atoms, events, and balances. Invalid vault spends do not erase circulating token authority. API reads include network and deployment txid; an external asset or v1 asset cannot enter v2 market routes.

V1 test assets remain versioned and read-only for market purposes. A clean v2 deployment is required for signet and mainnet rollout unless a separately specified, fully validated migration transaction moves each v1 balance into v2 outpoints. No historical heuristics assign token amounts to arbitrary UTXOs. The market stays disabled until ledger, builders, Guardian, indexer/DB, wallet, and mined Core competition/reorg tests in Beads `covedao-433` pass together.
