# Client transaction broadcasting

Implemented Beads epic `covedao-ut1` on 2026-10-03 and deployed to the existing Signet stack without migrations, bootstrap, or database reset.

Public launch, buy, sell, transfer, listing, purchase, and cancellation submission routes require `broadcast: "client"`. The backend validates wallet signatures, acquires the session claim before live RPC, retains both live fences and Guardian validation, finalizes, and saves exact signed bytes as READY. It returns `{network,status,rawTxHex,txid}`; marketplace responses also retain their session `fillId`. It makes no mempool acceptance, broadcast, or transaction-observation call in this path. Older public clients receive HTTP409 with refresh instructions before signing or RPC. Regtest retains its fixture relay unless explicitly requesting client preparation.

READY and existing BROADCAST responses replay exact stored bytes after unsigned-PSBT/transaction identity validation, without RPC, custody signing, or expiry rejection. Canonical protocol-accepted block events update matching READY sessions to BROADCAST inside the indexer's block transaction. BROADCAST records prior submission/observation, rather than current confirmation; canonical indexed activity remains authoritative after reorgs. Saved bytes can be resent after a reorg.

The browser verifies network, txid, and exact reviewed unsigned transaction before sending `sendrawtransaction` directly to the configured public RPC. Wallet scriptSig/witness finalization is allowed; inputs, sequences, outputs, version, and locktime must match. HTTP500 Bitcoin RPC errors are parsed; already-in-chain responses and ambiguous acceptance are handled using the expected transaction hash. Mismatching identities fail. Existing bounded concurrency, body limits, queue-inclusive deadlines, coalescing, and Retry-After handling remain. There is no backend broadcast fallback.

Bounded recovery records are scoped to network/payment account in localStorage, with at most10 records and4million serialized characters. Signed wallet PSBT data is saved before backend preparation; verified READY bytes are saved before relay. This permits explicit recovery from preparation response loss, broadcast response loss, or reload without a second wallet prompt. A pending-transactions panel supplies Retry broadcast and Dismiss. Browser storage must work before signing. Stored data consists of transaction/signature material, with no private keys or custody credentials.

Launch/trade and marketplace purchase/cancel callers use the shared helper. Transfer/listing HTTP routes use the same preparation path; existing presigned offer publication remains unchanged. Regtest developer wallets retain server relay.
